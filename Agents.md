## Session Start (mandatory, before any other work)

1. **Submodule update check:** run `.\sync-submodules.ps1` (double-clickable wrapper: `sync-submodules.cmd`). It attaches each submodule to its tracked branch (declared in `.gitmodules`), fast-forwards it, then commits the pointer bump(s). **Why a script and not automatic:** git pins one commit SHA per submodule — that is what makes a checkout reproducible. There *is* a track-latest mode (`git submodule update --remote`, which follows the `branch` declared in `.gitmodules`), but it has a cost that makes it unusable here (below). A submodule's upstream can move while this repo sits untouched (a push to `nui_wc2` from another machine is invisible here until someone advances the pin). Hooks don't help either — they fire on *your* git actions, and the drift happens over time with no action. So the sync is an explicit step; run it at the start of every work session. Keeping the pin at the upstream tip between sessions means running this same script on a schedule — there is no git mechanism that advances the pin while staying on the branch. **Never replace that fast-forward with `git submodule update --remote`:** it tracks the latest commit but checks each submodule out at a DETACHED HEAD, so the submodule has no branch and no upstream, VS Code has nothing to compare and stays silent, and the local branch rots unseen — `lib/nui_wc2`'s `main` had drifted 28 commits behind before anyone noticed (2026-09-11). Keeping each submodule ON its tracked branch is what makes drift visible: VS Code opens detected submodules as their own repositories and autofetches them, so the parent reports the submodule as modified the moment a branch tip passes the recorded SHA. Divergence fails loud instead of being papered over — nothing here edits a submodule, so local commits or a wrong branch means a human must look. **Checking attachment:** `git submodule status`'s `(heads/main)` parenthetical is `git describe` output and does *not* mean "on that branch" — it is true even in detached HEAD. Use `git -C lib/<name> symbolic-ref -q --short HEAD`. Windows gotcha (historical): the old napi `.node` binary was locked by the running server. `lib/ndb` is no longer used at runtime — nDB speaks HTTP (below) — so the submodule can be removed once no process holds it.
2. **Vendored SDK update check:** run `.\sync-vendor.ps1 -CheckOnly` (or double-click `sync-vendor.cmd`). It checks GitHub releases for `herrbasan/nVoice` against `lib/vendor.json` and notifies if an update is available. Run `.\sync-vendor.ps1` to sync release files into `lib/stt/` (`nvoice-client.js`, `tts-player.js`, `README.md`) and record the version. Diff `lib/tts/nspeech-client.js` against upstream `herrbasan/nSpeech` → `lib/nspeech-client/nspeech-client.js` as needed.
3. **nDB service check:** the backend talks to a standalone `ndb serve` daemon (default `http://127.0.0.1:8323`) over HTTP — there is no NAPI binding and no `lib/ndb` runtime dependency anymore (`sync-ndb.ps1` / `sync-ndb.cmd` / `lib/ndb-load-probe.js` were removed with the cutover). The service must mount `chat_users` and allow per-user database creation (`--dir <root>`); startup refuses to listen otherwise, naming the URL and the missing database.

## Operating Rules

- **Master IS live.** Work directly in `D:\SRV` on `master`; the server runs under nPM — coordinate stop/start with the user around backend edits and restarts.
- **Never put a query string on a JS module URL.** Modules are cached per full URL including the query, so `nui.js?v=5` in `index.html` plus the addons' bare `import ... from '../../nui.js'` evaluates the file TWICE — two module instances, where app-level config (image policy/rewrite hooks) lands on one instance while the other renders. Cost hours on 2026-09-11; symptom was "hooks silently do nothing" and `nui-list already defined` console errors. Instead, the server sends `Cache-Control: no-store` for `.html/.js/.css/.json` (images keep a 1h cache), so no cache-busting query is ever needed. Do not reintroduce `?v=` — edit and reload.
- Server does not auto-restart — restart after backend edits. A `Chat Backend running at …` log line means the process started, not that the command returned. Start servers in background; poll `/api/config` or `/health` for readiness (never an SSE endpoint — it hangs the request).

## Technical Spec — How This Codebase Works

Quick-access reference for an LLM arriving here. Deeper detail: [architecture-conversation-runner.md](docs/architecture-conversation-runner.md) (design authority) and [codebase-survey-bff.md](docs/codebase-survey-bff.md) (channel map).

### The model: conversation is a server-side session

A conversation is a **server-side session**; the browser is a **disposable attach/detach view** over `snapshot + events` (tmux model). Three load-bearing principles:

1. **Single author.** `server/runner.js` (the ConversationRunner) is the ONLY writer of conversation state. No client ever persists a message — this deletes the whole class of double-write guards.
2. **The store is canonical, the runner is a cache.** nDB holds the durable conversation doc (format unchanged). The runner holds the same messages in memory + the only non-recoverable state: the in-flight generation.
3. **The view is disposable.** Browser state is a projection of `snapshot + events`. Killing a tab changes nothing.

**One Runner per `{user}:{conversation}` pair** (the registry key is `${userId}:${conversationId}`, `server/runner.js:36`). "Per conversation", not "per tab": the same user's tabs/devices on the SAME conversation all attach to the ONE Runner; different conversations get separate Runners and run in parallel; different users never share a Runner (per-user `dbPath` isolation). Lifecycle: lazy mount on first attach/send → idle unload after N minutes with no views and no run → remount on demand. Server restart loses only `inFlight` (everything completed is already persisted).

**Concurrency — serialization is per-conversation, not global:** sends are always accepted — appended, persisted, broadcast immediately. A send is just an added prompt. What must never happen is concurrent **runs** (two gateway streams interleaving assistant output into one conversation) — runs serialize *within a conversation*; a send during an active run queues and batches into a follow-up run. Different conversations stream in parallel (independent Runners, no shared lock). Connection state carries no semantics: abort is an explicit API call; a closed browser is just one less listener.

### Event protocol (`GET /api/chats/:id/events`)

SSE, framed like embed-events (15s keepalive, drop the view on close). **On attach: one `event: snapshot`** — full state: `meta`, `messages[]` (stored form, `embedStatus` included), `inFlight` (if a run is active), `usage/context` of the last run.

Incremental events during a run:

| Event | Payload |
|-------|---------|
| `msg.user` | message (appended + persisted) |
| `run.start` | `{exchangeId, model}` |
| `run.retry` | `{exchangeId, attempt, attempts, reason}` — transient failure, runner re-issues the request; view clears the partial bubble |
| `delta` | `{content?, reasoningContent?}` — raw rate; the view debounces |
| `tool.start` | `{toolCallId, name, args}` |
| `tool.end` | `{toolCallId, name, status, resultMessage}` (result also persisted) |
| `msg.assistant` | message (appended + persisted) |
| `run.end` | `{finishReason, usage, context, aborted?}` |
| `embed.status` | `{messageId, status}` |
| `error` | `{code, message, raw?}` — gateway/provider errors relayed faithfully |

**Transient-failure retry (Copilot-style):** the gateway call retries up to `GATEWAY_ATTEMPTS = 3` (`server/runner.js`) on transient errors only — network faults (`err.cause`), stall/TTFT timeouts, HTTP 408/429/5xx. Deterministic rejections (4xx payload/auth/model errors) and user aborts never retry; all spent attempts fail loudly as before. Each retry broadcasts `run.retry` (the view clears the dead attempt's partials) and re-arms the stall/TTFT timers with fresh per-attempt state. When the run still fails, the persisted failure note carries `retryable` (default `true`; `false` for no-model and tool-hop-cap — their remedy is not a re-run) and the view shows a **Retry** button on the error bubble → `POST /retry`, which drops the trailing failure note(s) and re-runs the pending user turn.

Structural mutations (edit/delete/rename/clear): the runner re-broadcasts a full `snapshot`. No fine-grained mutation events. Attach mid-run: the snapshot carries `inFlight`, so the view renders the partial immediately and continues from live deltas. **No replay buffer, no offsets, no streamIds.**

### Runner routes (all cookie-auth, per-user DB isolation)

| Method | Path | Purpose |
|--------|------|---------|
| `POST` | `/api/chats/:id/send` | Append user message + start a run (queued if one is active). Body = raw stored-form fields (`content`, `attachments`, …). Returns `{exchangeId}`. |
| `GET` | `/api/chats/:id/events` | Attach to the conversation SSE stream (snapshot + live events). |
| `GET` | `/api/chats/:id/messages` | One backward page of older messages (`before`, `limit` ≤ 200) — the snapshot carries only the tail of a long conversation. Peeked slice + the shared `viewMessage` projection; never loads the whole document. |
| `POST` | `/api/chats/:id/abort` | Abort the active run. |
| `POST` | `/api/chats/:id/retry` | Retry the last failed run: drop the trailing failure note(s) + re-kick the chain. 409 when a run is active. |

Existing `/api/chats/*` CRUD (list/rename/pin/delete), `/api/search`, `/api/buckets/*`, `/api/user/settings`, `/api/models`, admin — unchanged.

### Stored data model (nDB)

- One conversation document per session (`_type: 'conversation'`, inline `messages[]`).
- Message **stored form**: `role`, `content` (timestamp-free by invariant — the prefix is projected at assembly from `createdAt`), attachments offloaded to `_file` nURIs, tool message shape (`toolName`/`toolArgs`/`toolStatus`/`toolImages`), assistant metadata (`reasoning_content`, `thinking_signature`, `streamStats`, `usage`, `context`), per-message `embedStatus`.
- **nDB reads return detached copies** (JSON over HTTP) — awaited re-reads at every use point, never cached across writes (`await runner.refresh()`). Objects held across writes go stale.
- Search index in shared `nvdb serve` v2 (`chat` collection): chunk IDs `${userId}:${sessionId}:${msgIdx}#${chunkIdx}`, native ACL `["user:<userId>"]`, promoted `role`/`mode`/`session_id`/`msg_idx`, native `created_at` range, hybrid RRF + Level-2 ONNX rerank. Users and auth sessions in the `chat_users` database (scrypt-hashed), conversations in per-user `chat_<username>` databases.
- **Message ordering is contractual:** the in-flight assistant message is persisted at its RESERVED position (`insertConversationMessageAt`, `atIdx` reserved at run start); queued sends append after it. Without this, an abort during a queued send produces an assistant-FINAL payload (providers treat as prefill; thinking-mode prefills 400).

### nDB v2 (HTTP) and the nDB -> nVDB sync

- **One client, no bindings.** `server/ndb-client.js` is the only nDB interface: `ndb serve` over HTTP/1.1 (default `http://127.0.0.1:8323`), zero dependencies, every non-2xx a typed `NdbError` carrying the engine's `code` (`not_found`, `cursor_expired`, `cursor_ahead`, `snapshot_expired`, `create_disabled`, `file_referenced`, ...). `ndb serve` owns the data; the Node process holds none. v3 (RAM-first) additions: `peek(id, {fields, textRanges, arraySlices, expectedSeq})` (seq-pinned partial read, 409 on a mismatched seq), `searchText({query, textFields, filter, sort, sortKeys, fields, limit, offset, cursor, maxScanDocs})` (the lexical lane used when nVDB is down), `getSchema()` / `setFieldMapping(mapping)` (the shared field/index mapping). Only the keys the caller asked for are sent — the engine is `deny_unknown_fields`.
- **Config:** `server/config.json` -> `ndbUrl`, `ndbUsersDb` (`chat_users`), `ndbUserPrefix` (`chat_`); overridable via `CHAT_NDB_URL` / `CHAT_NDB_USERS_DB` / `CHAT_NDB_USER_PREFIX` / `CHAT_NDB_TOKEN` (the tests use these).
- **Startup is gated:** `/health` must answer `ok`, `chat_users` must be in `/v2/dbs`, and every configured user's `chat_<username>` database is mounted or created. Creation needs `ndb serve --dir <root>`; without it the error names `create_disabled` instead of guessing. Idempotent indexes: `_type`/`id` hash, `updatedAt`/`createdAt` btree, plus `username`/`token`/`userId` on `chat_users` and `sessionId` on user DBs.
- **Per-user isolation is a database name**, not a path: `getOrLoadUserDb(user)` mounts `chat_<username>`. `dbPath` on a user doc is migration metadata only. Admin-created users get their database created before the user record is written.
- **Writes are atomic PATCH batches.** `arrayPush`+`set`+`set` chains became one `db.patch(id, ops)`; a batch containing an unresolvable path rolls back entirely. Reads return detached copies.
- **Pagination runs in Rust** (`POST /v2/dbs/:n/query` with `filter`, `sort: {field, dir}`, `offset`, `limit`, `fields`). `GET /api/chats` returns `{data, total, offset, limit}` and `db.queryAll()` pages until `total`, so nothing is silently truncated.
- **Buckets:** `storeFile(bucket, buffer, filename)` -> `{ref, hash, ext, size}` (full 64-hex SHA-256 for new files), `getFile(bucket, "hash.ext")`, `releaseFile(bucket, "hash.ext")` (409 `file_referenced` while a live or restorable document points at it). The `/api/buckets/...` route accepts **both** 8-hex legacy ids and 64-hex ids.
- **Sync engine (`server/nvdb-sync.js`)** keeps the shared `chat` collection in line with each user database:
  - the watermark (`{_type: 'nvdb_watermark', key: 'nvdb_wm_<username>', source_epoch_uuid, synced_seq}`) lives in **`chat_users`** — writing it into the user's own DB would advance that DB's `last_seq` and the sync would chase itself forever (nDB assigns `_id`, so the doc is addressed by `key`);
  - same epoch and `synced_seq < last_seq` -> replay `changes(seq, limit 250)`, rebuild only the touched conversations/sessions, delete orphaned chunk ids, commit, then advance the watermark **after** the nVDB commit;
  - `delete` events carry no document body, so they trigger a live-session sweep (this user's fingerprints vs the live session ids);
  - no watermark / epoch changed / `409 cursor_expired` / `410 snapshot_expired` -> pinned-snapshot rebuild with a BLAKE3 envelope hash-diff (unchanged chunks keep their vectors), watermark saved, then one incremental catch-up pass. A 410 is retried from a fresh snapshot up to twice (the pin lives 300 s), then thrown;
  - `reconcileUserNvdb(instance, { forceVerify: true })` (the watchdog path) also proves the user's slice still EXISTS: with `synced_seq === last_seq` it checks the per-user fingerprints, and when they are empty while the user DB still holds conversations it logs `nvdb appears wiped for user; rebuilding from snapshot` and rebuilds. Never test the SHARED collection's `doc_count` — with several users mounted it says nothing;
  - same-epoch `synced_seq > last_seq` (and `409 cursor_ahead`) throw loudly — the monotonic seq invariant is broken.
- **The vector drain is `createVectorDrainer`** (`server/nvdb-sync.js`, exported): `server.js` wires the ONE function its timers/`afterSync` call, and the tests call the same function with stub embed deps. `userFingerprints` is a `createNvdbSync` member (the #69 bug was a bare reference to a copy of this loop that lived in `server.js`). It checks `isEmbedAvailable()` then `instance.drainRunning` BEFORE any work, holds the guard for the whole run, attaches per-8 vectors, and marks a message `embedded` only when every chunk has one.
- **nVDB is a MIRROR and may be down** (`server.js`): `isNvdbUnavailableError(err)` (in `nvdb-v2-client.js`) matches network/transport faults (`ECONNREFUSED`/`ECONNRESET`/`ETIMEDOUT`/`UND_ERR_*`/`fetch failed`/abort) and HTTP 5xx, never 4xx. Boot with nVDB unreachable logs loudly and runs degraded instead of exiting. Every post-commit mirror call (`embedMessageAsync`, `syncShiftedTailToNvdb`, chat delete, the drain) calls `markNvdbFailure(instance, err, ctx)` — WARN, `nvdbOnline = false`, `instance.nvdbDirtyGen++` — and never fails the already-persisted nDB write. A single-flight 15 s watchdog (unref'd, 3 s health probe) reconnects, runs `ensureNvdbCollection()`, and reconciles every mounted instance with `{ forceVerify: true }`; while online it drains `nvdbDirtyGen > nvdbSyncedGen`.
- **Search degrades to nDB text** (`internal-tools.searchArchive`): when `hybridSearch`/`level2` throws an unavailable error (or no client is wired on a `searchText`-capable handle) it calls `deps.onNvdbError(err)` and answers from `db.searchText` — same role/mode/date filters, all query tokens required, scored by phrase + token frequency + recency, paged by cursor under a 10k-doc / 50-page budget (`truncated` marks an abandoned cursor). The response carries `method: 'ndb-text-fallback'`, `engine: 'ndb'`, `degraded: true`, `truncated`, `nvdbError`; `/api/search` returns it as-is.
- **Tests:** `node server/ndb-http-e2e.test.mjs` (multi-DB + `createDb`, PATCH atomicity, Rust pagination, buckets incl. legacy 8-hex, all four sync paths, the v3 `peek`/`searchText`/schema surface, the real vector drain `#69`, the nDB-text search fallback, the `forceVerify` wipe rebuild, the 410 snapshot retry) and `node server/nvdb-v2-e2e.test.mjs`; both spawn throwaway `ndb.exe` / `nvdb.exe` on ephemeral ports in a temp directory. `node server/archive-search.test.mjs` covers the mocked hybrid path.

- Aborted runs persist **content only** — reasoning cut mid-stream is a malformed thinking block.

### Context & cost management

- **The runner counts, not the gateway.** `server/token-count.js` (`countApiMessages`/`breakdownApiMessages`, js-tiktoken cl100k/o200k) is fed the full field set (content + reasoning_content + tool_calls + tool results + image costs). The gateway's own estimate only reads `content` and under-counts thinking/tool chats by 58–91%.
- `_assemblePayload()` in `server/runner.js` is shared by `runOnce` (live turn) and `buildSnapshot` (on-load) — identical payload → no load/send flip. **The context pill = the on-the-wire payload** (what the next request consumes), not raw stored history.
- **Time signal is input-only** (`server/api-view.js`, 2026-11-27): exactly one `[YYYY-MM-DD@HH:MM]` prefix on every **user** and **tool** message, derived from stored `createdAt` (immutable → cache-stable, never parsed from content); **assistant turns carry none**. Stamping the model's own replies was the mimicry engine — it copied the format from its own past output while the system prompt forbade it. The model now reads the prefix as a label the system puts on *input*, and the newest stamp *is* "now". The system prompt keeps the day anchor (`Date:`) and describes the convention instead of banning timestamps. **Strip shapes are one definition (`TS_SHAPE_SRC`) and accept `@`, `T` and space separators plus optional seconds** — the model invents ISO-ish `[YYYY-MM-DDTHH:MM]` rather than copying ours, and an @-only strip let 156 such echoes persist, where they re-taught the pattern every turn. The widened shape runs at persist (runner), at projection, and in the view's legacy split.
- **Measures** (audited against "saving must exceed cache-break cost"): retirement/tombstones (breaking by design — batch them), unretire, merge/auto-heal. Dedup/chunking was REMOVED 2026-10-11 (issues #52/#53): replayed across all chunked sessions it saved ~1 MB total vs the retirement's 6.1 MB, and hash-label transcription caused confabulated ids. Do not resurrect it; the design lives in [architecture-conversation-runner.md §2.3a](docs/architecture-conversation-runner.md).
- **Retirement is positional** (`server/retire-view.js`): retirement chats stamp each payload message `[mN]` (N = stored index); `context_retire(messages, distill)` takes indexes/ranges and retires whole messages (tool result, reasoning, prose, user text, write-args). `context_units()` enumerates. Partial success — unknown indexes are skipped, not fatal. The live chain (last user message onward) is never tombstoned. **Usage policy: exceptional, not routine** — only when context is genuinely running low or the user asks for focus; the KV-cache economics (one expensive request, cheaper requests after) are stated in the tool description and convention paragraph.
- **Retirement keys are content hashes** (`fnv1a`, byte-identical to the old chunk engine's key forms — tool results hash the timestamped API form, write-args the raw field value) so pre-rework retirements keep matching. Unsigned reasoning retires by replacement; signed reasoning (thinking_signature) drops together with its signature.
- **Legacy label defense stays**: the runner scrubs `[chunk_…]` labels from outbound tool args (leading stripped, bare rejected) and strips echoed `[mN]` markers from args and from persisted assistant content — addresses are view-only, never content.
- **Per-provider prior-reasoning policy** (in the gateway, `capabilities.priorReasoning`; the chat `api-view` strip was REMOVED — reasoning passes through verbatim):

| Provider | `priorReasoning` | Why |
|----------|------------------|-----|
| DeepSeek | `keep-with-tools` | No-tools: prior reasoning ignored → strip free. With tools: omitting → API 400. |
| OpenAI | `strip` | Silently **ignored**, not rejected; keeping is pure token waste. |
| xAI (Grok) | `keep` | Omitting prior reasoning = documented #1 cache-miss cause. |
| Anthropic | `keep` | Structured thinking blocks with signatures must round-trip verbatim during tool use. |
| Kimi | `keep` | `reasoning_content` always present and must be echoed. |
| z.AI (GLM) | `keep` (with `clear_thinking:false`) | server-side clear default; retaining keeps the prefix append-only. |
| unknown | `keep` | cache-safe default. |

- **`thinking_signature`**: assistant reasoning is only kept on the wire when it carries a signature (Anthropic contract guard). Unsigned reasoning = poison, dropped.

### Tool execution (server-side)

Tools run in the runner, not the browser. `server/mcp-pool.js` (per-user MCP pool, JSON-RPC, settings-sourced config) + `server/internal-tools.js` (archive/storage/fetch). Runner tool loop: `tool.start`/`tool.end` events, single-author tool messages, 12-hop cap, server-side recursion. MCP images → internal buckets. **Preview is pure view** — the tool returns data; the view renders a preview affordance from `tool.end`. Server-side reach *increases* vs the old browser-bound tools (no CORS). `browser_fetch` is the one place CORS used to be an accidental guard — log every call.

### Forward roadmap (not yet done)

- **P2 — nPort cutover:** bind all services to localhost/127.0.0.1, close direct ports, public surface = 443 only. OPNSense forwards 80/443; nPort runs as a Windows service (nssm). Verify `/health` + `/v1/models` via public domain.
- **P3 — Multi-user data-layer enforcement (family model):** every memory/storage record gets `owner` (usr_id). Write/delete requires `sub == owner`; read is family-wide. No ACLs/groups — family-only. Reconcile chat `users_db` with nPort identity (nPort owns WHO, chat owns WHAT keyed by `sub`).
- **P4 — Token hygiene (nPort):** `label` + `createdAt` on all tokens; session tokens get `exp`; server-side `exp` enforcement; kind policy (sessions vs apikeys gated per surface); revoke stale test sessions.
- **PD cutover remnants:** dead browser orchestration (`client-sdk.js`, `mcp-client.js`, conversation state machine) awaits removal; arena summary generation + legacy import still direct-gateway.

### Open questions

- **Memory privacy exception:** twin/biography/psychology memories may need a private scope overriding the family-readable default.
- **Chat `users_db` migration:** adopt nPort identity for login, keep per-user profile data keyed by `sub`? Decide at P3 kickoff.
- **Context alignment (unresolved):** the user reports mutual understanding drifts on very long conversations. Hypothesis: stripping prior reasoning removes the model's visible chain-of-thought, so misreadings compound instead of self-correcting. Experiment (do NOT assert without it): same long task, same model, reasoning kept vs stripped, compare felt alignment. Per-provider policy is the likely fix.

## Invariants That Survive the Refactor

- **NUI components only** for UI controls (`nui-input`, `nui-select`, …) — never raw HTML controls. Style via theme variables (`--color-base`, `--text-color`, `--nui-accent`, `--nui-space`, …), not custom CSS on components.
- **Code style:** 4-space indent, single quotes, semicolons, ES6 modules. Flat explicit logic; dense colocation; minimal comments (structural markers only).
- **Long conversations are tail-loaded, never fetched whole on attach** (Track 2a). `Runner.init()` does one session read, one `_id`-only conversation query, and `convStore.loadConversationTail` — a `POST /doc/:id/peek` window of the last `TAIL_PAGE_SIZE = 25` messages, snapped back to a turn boundary (unbounded backward walk: a 30-message tool chain must be crossed whole, never cut). The snapshot's `messages` is that window with absolute `idx`, plus `baseIdx`/`totalMessages`/`hasMore`/`convSeq`. The view paints that tail with no spinner and no artificial delay (`_vsActivateWhenReady` is one `requestAnimationFrame`; nui-markdown renders synchronously), then — if `hasMore` — hydrates the ENTIRE remaining prefix `[0 .. baseIdx)` in ONE background request right after the first painted frame: `GET /api/chats/:id/messages?before=<baseIdx>&all=1` → `loadConversationPage({ all: true })`, one peek from offset 0. There is **no pagination UI and no scroll-top trigger**: `_hydrateFullHistory` prepends the fragment above the existing tail, restores the scroll anchor (or the bottom pin), and re-activates virtual scroll — all in one synchronous tick, so no flash and no jump. `viewMessage` **omits `rawContent`** (it duplicated `content` byte for byte on every projected message; stored docs keep it). **`db.get` on a long conversation is the bug this path exists to prevent.** Three rules follow: (1) every mutating or payload-assembling path starts with `refresh()` (the FULL load, which supersedes a partial tail) or `ensureFull()` — audit any new `this.conv.messages` reader for it; (2) the snapshot's tiktoken path may only run when `_fullLoaded`, and the zero-tiktoken reuse only when the window ends at the conversation's end; (3) `fields` on `peek` is load-bearing: the engine returns ONLY the named fields alongside `array_slices` (it does not fall back to all top-level fields), so `CONV_META_FIELDS` must list every top-level conversation field. The virtual scroller's viewport math subtracts `stage.offsetTop`. Test: `server/runner-tail-load.test.mjs` (500 messages, real `ndb serve` — paged reconstruction AND the one-shot `all: true` prefix).
- **Data model:** one conversation document per session (`_type: 'conversation'`, inline `messages` array with per-message `embedStatus`). Vectors in nVDB keyed by message ID with `{ chatId, msgIdx }` payload. Users in the `chat_users` database (scrypt-hashed), conversations in per-user `chat_<username>` databases — reconciled with nPort identity at P3.
- **A new chat is a client-side draft until it is started** (#60). `New Chat` opens a setup card in a container keyed `DRAFT_CHAT_ID` (`'__draft'`) and writes nothing; `Start chat` or the first send materializes it — one `POST /api/chats` carrying the card's model/title/instructions (`_materializeDraft`), then the container/maps are re-keyed to the server id. `Cancel` (or Escape while focus is inside the card) returns to the chat New Chat was pressed from, and the card offers no Cancel at all when there is no conversation to return to. Switching to another chat discards a draft outright, so an abandoned New Chat can never accumulate an empty conversation (the DB had 437 sessions at the time this shipped). The card's model list comes from the same `buildModelSelectItems` the sidebar uses. The first `msg.user` retires the card/welcome (`_runnerUser`) because the attach-snapshot can land *before* the send and re-render the empty state above the first message.
- **Embedding pipeline** (server-side, stays): fire-and-forget after message POST, startup reconciliation nDB↔nVDB, SSE `embed-status` events, retry with escalating backoff.
- **Image lifecycle:** base64 intercepted client-side → bucket upload → lightweight URL in message JSON. On chat delete, refs are garbage-collected via `db.releaseFile` (orphans → `.trash`).
- **Tool execution is server-side** (runner `mcp-pool` + `internal-tools`); the view renders `tool.start`/`tool.end` events. The browser no longer runs tools, assembles system prompts, or orchestrates the gateway — it is a view over the runner's snapshot + event stream.
- **Voice input is nVoice behind the `/api/stt` relay** (vendored SDK `lib/stt/nvoice-client.js` and `lib/stt/tts-player.js` via `.\sync-vendor.ps1` — update via script, never edit in place). Two modes: dictation (mic button, input-integrated) and assistant (per-conversation `assistantMode` meta → reactive turn-taking with desktop status dock / mobile hands-free view + system-prompt voice block + sentence-streaming TTS). `voice: true` stored-form field marks spoken user messages.
- **Narration blocks speak through the app's own TTS controller** (MD-Blocks §5.2 `preset=narration` = delivery text — spoken, not shown). `nui-markdown` creates the play control only when a speech function is registered, so `chat/js/chat.js` registers `nui.util.setMarkdownSpeech` at init and the block itself is the controller's target (one global playback, target identity = the block, so bubble and preview playback never interleave). The control's icon/label are written back from controller state — nui's own two-state flag cannot see a line that simply finished playing, and it flips its own visuals on every click. Self-injected markdown (`updateAssistantContent`'s `markdownToHtml` branch) must call `nui.util.enhanceNarration` afterwards: the component render that creates the controls never runs on that path.
- **A message holding MD-Blocks structure takes the bubble width** (`.chat-message:has(nui-markdown.nui-md-document)`, `chat/css/chat.css`). Blocks structure makes the element an inline-size container, and containment makes a shrink-to-fit host measure as if empty — the bubble collapsed to a min-content sliver. That is the #52 failure mode reached through blocks instead of plain markdown, and it bites hardest now that a one-line narration block can land in any message. Plain messages still hug their text.
- **Hosted tool apps are explicit and headless-first** (`chat_app_open`, #58). Ordinary tools such as `print.render` stay UI-free and return their normal render artifacts. Only an explicit `chat_app_open` call returns a conversation-scoped `appInstanceId` plus a `ui.kind = 'hosted-app'` action; the user must click its Open button before `chat/js/hosted-app.js` opens the large `nui-dialog`. App ids and editor paths are allowlisted (`print` → `/print` on the configured MCP origin), credential-bearing URLs are rejected, and the iframe is sandboxed. The app talks directly to its own backend — chat never proxies saves or shares chat credentials. For lifecycle events, the client adds `hostInstanceId` and the real `parentOrigin` to the editor URL; `/print` accepts host notifications only for configured chat origins. **Public deployment:** `MCP_PUBLIC_ORIGIN=same-origin` makes hosted URLs use the browser's actual application origin, never the backend localhost/LAN address. nPort must expose authenticated path-preserving `/print/*` and `/storage/*` routes to MCP, and `agents.print.parentOrigins` must include the public chat origin (and LAN mirror when used). The parent validates exact origin, `event.source`, instance and schema, then `POST /api/chats/:id/app-events` revalidates the instance against the persisted `chat_app_open` tool message. Saved/closed events are deduplicated, appended to the conversation's `appEvents`, broadcast as `app.event`, and included in the next live system payload; only a successful run marks them consumed, so snapshots and failed runs never drop them. Save success remains independent of notification success — the editor reports notification failure separately.
- **Preview state is per conversation session, not per pane.** `chat/js/preview.js` keeps one record per session id (`items`, `activeId`, `paneOpen`, `browserOpen`, `notes`, marks live on the item) in a `sessions` map; the pane DOM is the ONE shared surface, so `preview.setSession(chatId)` is what switches chats — it saves the outgoing record and loads the incoming one, restoring that chat's preview instead of wiping it (`switchChat` on a real chat id, `startNewChat` on `DRAFT_CHAT_ID`, `_materializeDraftSession` on the new id, and once at boot after `preview.init()`). `preview.clearSession(chatId)` runs on chat delete (and on draft discard). A background chat's tool call never hijacks the visible pane: `show`/`showUi` take `{ sessionId }` (the runner's `_runnerToolStart` passes the run's `chatId`), update that session's record, and touch DOM only when the target is the current session — re-checked after an `await` in url mode, so a chat switch during the fetch does not paint the wrong pane. `consumeMarks(ids, { sessionId })` clears the marks of the session that sent, not whichever chat happens to be visible. `preview.reset()` (all sessions) is the logout/hard-reset path only.
- **The preview pane carries its own storage browser and a live context for the next turn** (Preview Surface Milestone 1). The pane is reachable at any time from the app header (`#preview-toggle-btn` → `preview.togglePane()`); on a blank chat it opens the `nui-file-tree` browser, whose provider lists storage lazily through the same-origin `/storage/*` proxy (rooted on FIRST open, so a chat that never browses issues no requests; `.backups`/`.trash` are hidden). Selecting a file calls `preview.show({ url: '/storage/…', … })`, and a docked (mobile) pane collapses the browser so the content gets full width. The browser column is resizable (`#preview-browser-resizer` sits between the tree and `.preview-main-col`, driven by `nui.util.enableDrag`, clamped to `160px…min(520px, body − 220px)` so the content never collapses, persisted as `preview-browser-width`; the splitter is hidden with the browser and on a docked pane). `#preview-content` keeps a reading measure (vertical `2rem … 3rem`, sides clamped `1rem … 2.5rem` against the pane width) while deck and `ui` modes stay flush at `padding: 0`. `preview.getContext()` returns what is on screen (`{ paneOpen, id, path, title, kind, view, marks }` or bare `{ paneOpen: true }`, `null` when closed); `sendMessage` attaches it as `previewContext`. The server validates it (`conversation-store.validatePreviewContext`, 400 on anything malformed — size caps throw, never truncate), persists it on that USER message, and `api-view.formatPreviewContextBlock` appends it to that turn's **wire content only**: stored content, the system prompt and every earlier turn stay byte-identical so the KV-cache prefix is untouched. `/storage` (no trailing slash) and `/storage/` both reach the proxy — the route is matched BEFORE the trailing-slash `index.html` normalization, which used to turn the root listing into `/storage/index.html`.
- **Passage marks are text, and the selection toolbar belongs to the document view** (Preview Surface Milestone 2). Selecting prose in a markdown document opens `#preview-selection-toolbar` (Speak / From here / Mark, clamped inside the pane, `mousedown` cancelled so the click never collapses the selection it acts on); marks accumulate in `#preview-marks-bar` above `#preview-content` inside `.preview-main-col` and ride the next turn through `preview.getContext().marks`. Three load-bearing rules: (1) a mark stores **normalized text + occurrence + heading**, never DOM offsets — every render builds a fresh `nui-markdown` (`_processed` guard), so offsets are stale while text survives; resolution re-collects the text map per mark (`chat/js/preview-marks.js`). (2) **Never `Range.surroundContents()`** — it throws across `<strong>`/`<code>`/`<a>`; each intersecting text node is split and wrapped in its own `<mark class="preview-passage-mark" data-mark-id>`. (3) Marks are consumed **only after `res.ok`** (`sendMessage` captures `getActiveMarkIds()` before the send and calls `consumeMarks(sentMarkIds)` on success) — a failed send keeps them for the outbox retry, and a mark added mid-flight is not in the sent list so it survives. A mark whose passage no longer resolves after the CONTENT changed (the model rewrote the file via `chat_preview_show`) is dropped — the revision already happened; unresolved against unchanged content is logged instead. Deck view keeps the marks (bar visible) but highlights nothing; jumping from the bar returns to document view. `MAX_MARKS=20` / 4000-char quotes / 1000-char notes mirror `validatePreviewContext` — a rejection is shown in the bar, never silently truncated.
- **Multi-format preview is one explicit type table** (Preview Surface Milestone 3). `chat/js/preview-file-types.js` is the ONLY extension/MIME map: the file tree open, `preview.show` in both modes and the Content-Type fallback all classify through `kindFromName`/`kindFromMime`, so an unknown type can never reach a text decoder — it lands on the same readable unsupported-format error (filename + MIME), and nothing falls back to UTF-8 decoding of arbitrary binary. `pdf` is classified now but renders a "not available yet" card (Milestone 4). URL mode classifies BEFORE fetching: `image|svg|audio|video` are passive — the item carries `{ kind, url }` and the renderer uses the resolved url directly (never prefetched; SVG is an `<img>`, never inline markup), `docx` is read as bytes (25 MB cap) and converted client-side, `markdown|code|html` keep the text proxy, an unknown extension gets one same-origin HEAD whose Content-Type decides. `html` renders in `<iframe sandbox="allow-scripts">` via `srcdoc` — no `allow-same-origin`, forms, popups or top navigation; the allowlisted hosted-UI frame (`kind: 'ui'`) is unchanged. DOCX is zero-dependency (`chat/js/preview-docx.js`): hand-walked ZIP central directory + `DecompressionStream('deflate-raw')`, a DOM-free XML→paragraph model, then `createElement`/`textContent` only (tables, images, headers/footers are ignored, never injected as markup). Media and HTML frames drop the reading padding (`.preview-content.media-mode|html-mode`); `.preview-unsupported` is the readable dead-end with an open-in-new-tab control. Every `await` in `show` is followed by the `targetId === currentSessionId` check, and `getContext().kind` reports the real kind (not "everything non-markdown is code").
- **The preview has two views for markdown.** Document flow is the default; slide view renders the same source through `nui-slides` (one section = one slide, toolbar, fixed 16:9 canvas scaled to the pane). The toggle appears only when the document has deck structure — an `mb:` marker, or a root-level `---` after frontmatter is stripped — because a document with no sections is a single overflowing slide. Deck mode builds a fresh `<nui-slides>` around a fresh `<nui-markdown>` (never `show-breaks`, since each section is already a slide) and `.preview-content` drops padding and scroll so the canvas can be measured. The deck stays in natural flow rather than `height="fill"`, so a tall pane leaves blank space below instead of stretching and letterboxing the 16:9 surface. The view is per item, defaulting to the last one used (`preview-view`).
- **Section separators are a preview-only affordance** (`chat/js/preview.js` sets `show-breaks="Slide"` on the element it builds — attribute set BEFORE appending, because the component reads its options once at render and its `_processed` guard ignores later changes). The preview is the deck-authoring surface, so it labels boundaries "Slide N of M"; the message path stays untouched, and the streaming path (`beginStream`/`appendChunk`/`endStream`) can never have them — it renders block by block, so it cannot know the total. Note a root-level `---` is a section break, not an `<hr>` (MD-Blocks §9), so any previewed document written with `---` rules gets labelled. The label rides in `data-label` + `::after` and never enters `textContent` — never read or measure it as text.
- **Knowledge-base ("research note") links open as a dialog in the preview** (`chat/js/research-note.js` + `preview.js`). The blog's convention is a note page at `references/<slug>.md` reached by a relative link (`../references/x.md`; a note citing a neighbour writes it bare, `x.md`) — raum.com's build bakes one `<dialog>` per cited note into the page and its `chrome.js` opens it on click. A preview has no build, so the link is detected in the rendered markdown (path-based, on the **resolved** destination — bare note→note links carry no directory) and the note source is fetched from the document's own base into one reused `nui-dialog` panel: title from frontmatter (the body's duplicate H1 is dropped), scrollable body, open-in-new-tab + close chips, backdrop/Escape close, one note at a time (a note→note link swaps the panel). Resolution needs `item.base`; a content-mode document has no location, so the note's `references/` tail is assumed to sit in storage `blog/references/` and that assumption is logged. Note anchors are the one link class that does NOT open a tab on a plain click.
- **Links in rendered markdown always open a new tab** — never navigate the SPA away (that would throw the conversation away). Two mechanisms, deliberately split: `chat.js onMarkdownLinkClick` covers message markdown (any `<nui-markdown>`; preview anchors are already handled/marked and skipped), and `preview.js` resolves anchor destinations against the document base, stamping absolute `href` + `target=_blank` via a `MutationObserver` on `.preview-content` (every render rebuilds anchors, and `nui-slides` clones them for its slides — decoration follows the DOM, not the render call, and rAF is unusable here because a hidden page never fires it). Storage-origin destinations are rewritten to the same-origin `/storage/*` proxy path (`browserHref`), because the MCP origin binds localhost on the server host and a remote browser cannot reach it.
- **A chat reading at the bottom stays at the bottom across layout changes.** One `ResizeObserver` per `.conversation-container` (`trackBottomPin`, chat.js) covers every trigger that shrinks the message column — window resize, the preview split and its drag, a growing composer — because they all resize that container. "At the bottom" is sampled on **scroll** (≤100px, the tolerance the streaming auto-scroll already uses), never in the observer: the observer runs after layout, when the distance from the bottom has already grown, so the pre-resize reading is the only honest input. One more pin is required and easy to miss: the virtual scroller re-measures every slot ~300ms after the last resize and rewrites the stage height then, moving the bottom *again* — an immediate pin alone leaves the newest message ~4k px out of view on a widened preview split (measured 2026-11-08), so the settle path (`_vsRecalculate`) calls `repinIfStuck` too.
- **The separator renders because `lib/nui_wc2` carries two fixes (uncommitted)**: the `hr`'s UA `overflow: hidden` clipped the rule away (nui_wc2#78), and the zero-height box let the absolutely positioned label land on the next section's first line (nui_wc2#79 — the label is now an in-flow line with `padding-top`, since a child's margin collapses through the borderless box). If `lib/nui_wc2` is ever rolled back before those land upstream, the separators silently become blank space or paint over the following heading again.

## Security

- Cookie-only auth (HttpOnly), same-origin by default, no secrets in frontend.
- `nui-markdown` escapes `& < >` before formatting, but attribute-value/URL-scheme hardening is a known gap owned by **nui_wc2** — don't build markdown sanitization here.
- nPort cutover (P2) binds services to localhost; public surface becomes 443 only.
